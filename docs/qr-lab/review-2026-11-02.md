# Simulator review — 2026-11-02

This pass improved web startup, the 3D simulator's blur path, worker failure
handling, native input validation, and the Expo example's clean-install
configuration. QR detection/refinement algorithms and public result schemas
are unchanged.

## Changes and measurements

| Area | Before | After |
|---|---|---|
| Initial media UI JavaScript | 1,193.11 kB (330.46 kB gzip) | 255.23 kB (79.48 kB gzip); Three.js/Scene3D loads when selected |
| Blur canvas allocation | Two canvases and an input copy every frame | Two retained canvases, resized as needed; normal input buffers use a view |
| Worker failure/disposal | Pending initialization/scans could remain unsettled | Initialization, both scan slots, and preset requests reject; failed client cannot be reused |
| Swift bridge dimensions | Integer conversion/arithmetic could trap the process | Exact UInt32 conversion and checked byte-count arithmetic return an input error |
| Expo example setup | Metro could not resolve nested `@expo/log-box`; linked source failed TypeScript resolution | Hierarchical dependency lookup and explicit example-local Expo type resolution |

Initial entry size fell 78.6% (75.9% gzipped). This defers the 3D dependency;
it does not remove that code from users who open the simulator. The built
Scene3D chunk is 939.20 kB (252.55 kB gzip), and still triggers Vite's chunk
size advisory.

Blur measurements: Apple M2 Max, Chrome 156, square RGBA frames, sigma 1.5.
Each size used 35 interleaved old/new runs, alternating execution order,
discarding the first five, then taking the median of 30 samples per path.

| Size | Previous blur | Reused canvases | Reduction |
|---|---:|---:|---:|
| 640 × 640 | 2.10 ms | 1.10 ms | 47.6% |
| 960 × 960 | 2.90 ms | 1.90 ms | 34.5% |
| 1280 × 1280 | 4.20 ms | 2.80 ms | 33.3% |

These are local blur microbenchmarks, not end-to-end scanner speedups.
The [browser harness](../../debug-ui/scripts/check-blur.browser.ts) also
confirmed byte-for-byte output parity for five cases covering transparent
pixels, input subarrays, repeated frames, sigma changes, and resizing. Ten
applications allocated only two canvases, preserved inputs, and left prior
output buffers intact.

Repeated readback initially caused Chromium to change canvas rendering
paths and introduce small pixel differences. Explicit
`willReadFrequently: false` on the destination preserved the fresh-canvas
result in this browser. The destination is cleared before each draw to
prevent translucent pixels accumulating. Browser parity should be rerun
when changing this path or browser engine. See the official
[Canvas context settings](https://html.spec.whatwg.org/multipage/canvas.html)
and [Chrome Canvas 2D documentation](https://developer.chrome.com/blog/canvas2d/).

## Browser simulator verification

Tested with Argent against both Vite development and a production preview:

- Production media startup loaded the entry and worker without Scene3D;
  selecting **3D Scene** loaded the deferred chunk and decoded one QR code.
- Blur at 1.2 px preserved decoding at 640, 960, and 1280 resolutions.
- Fisheye at 50% strength, 1280 resolution and 1.2 px blur decoded with
  calibration enabled; mean corner error was 0.06 px. Disabling calibration
  still decoded, with error 2.81 px; re-enabling restored calibration.
- Screenshots showed the simulated image and aligned detection overlays.
- The [worker harness](../../debug-ui/scripts/check-scanner.browser.ts)
  verified actual WASM initialization failure, a runtime worker crash,
  disposal with pending requests, classic and robust decoding with capture,
  and session scanning/reset using `near_00`. Caller pixels stayed attached.
- Forcing the live UI's scanner to dispose and then switching fixture showed
  an error banner while preserving the interface. Reload restored operation.
- Normal production operation produced no runtime errors. The existing
  Three.js `Clock` deprecation warning remains.

## Expo iOS simulator verification

Rebuilt the Rust iOS libraries and Expo native app, then installed on
iPhone 17 Pro / iOS 26.0. Metro used port 8084 because 8082 was occupied by
another project. `serve-sim` injected `fixtures/near_00.png`, with mirroring
off, into the native camera pipeline.

- The preview decoded `Q:near_00:0` with refined corner overlays.
- The app reported approximately 6 fps, 1280 × 720 source frames,
  1080 × 608 working frames, and approximately 3.4 ms scan wall time.
- Pause switched the app to IDLE; Resume restored scanning.
- All ten checks in
  [check-native.simulator.js](../../bindings/expo-cpu-scanner/example/scripts/check-native.simulator.js)
  passed against the actual Swift/C module, including recoverable overflow
  rejection followed by valid scans.
- The connected runtime log registry was empty after these checks.

The same generated Expo app failed before JS startup on iPhone 18 Pro /
iOS 27.0, with `SIGTRAP` at
`___UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption_block_invoke`.
The generated app's missing scene lifecycle adoption remains a compatibility
issue; this pass did not migrate the Expo app lifecycle. Android and physical
devices were not exercised.
